# Copy memory benchmark

Объяснение задачи, оптимизаций и измерений с примерами графиков:
[Как уменьшить расход памяти ch-backup и проверить результат](OPTIMIZATIONS.md).

## Сравнение реализации с ограниченной памятью

Ветка `feat/copy-bounded-memory` сравнивается с baseline `127ea3c`. Для каждой
точки обе версии читают один исходный backup и используют разные target-префиксы.
`probe.json` сохраняет путь импортированного пакета и SHA-256 его Python-файлов;
это позволяет проверить, что baseline действительно импортирован из worktree.

```sh
make test-benchmark-copy-memory-ab \
  BENCH_PARTS=10000 CLICKHOUSE_VERSIONS=26.3.12.3 \
  BASELINE_REF=127ea3c CANDIDATE_REF=HEAD BENCH_REPEATS=3 \
  BENCH_ARGS='--total-budget-hours 12 --cleanup-timeout 1800'
```

`BENCH_PARTS=N` и `CLICKHOUSE_VERSIONS` должны содержать ровно одно значение.
Оба Git ref должны быть доступны локально. Харнесс фиксирует их SHA в `options.json`
и создаёт отдельные worktree в `staging/benchmark/sources/<серия>/`; основной checkout
не переключается. Candidate по умолчанию — `HEAD`; незакоммиченные правки в него
не входят. Общий исходный backup готовится один раз кодом собранного wheel.

Каждый повтор сравнивает A и B на одинаковом backup и разных пустых target-префиксах.
Порядок A/B меняется между повторами; fresh и resume одного варианта используют
один target. В `report.md` и `comparison.json` попадают медианы времени, учтённого CPU,
пиков main/worker и суммы RSS по выборке только для успешно завершённых пар.
Профилированные повторы в основное сравнение не входят. Кеши ОС не сбрасываются;
это сравнение с прогретыми кешами, а не cold-start тест.

По умолчанию A/B измеряет planning, а для metadata v5 ещё metadata-only и resume.
Для полного копирования всех S3-объектов добавь `--copy-mode full` в `BENCH_ARGS`.
При большом N полный режим может занять несколько суток. CPU/RAM-профили снимаются
для обоих вариантов после обычных повторов, до удаления окружения.

Перед большой лестницей нужен полный smoke на двух партах со 120 колонками
для обеих схем metadata: версии 25.8.23.13 и 26.3.12.3. Тяжёлые профайлеры работают
в отдельных повторах после основного A/B. Не запускать сравнение
одновременно с другой серией на той же VM.

В candidate декомпрессор выдаёт chunks не больше `filesystem.chunk_size`.
Metadata записываются в приватные временные tar-файлы; воркер получает только путь.
Планы, listing и digest журнала находятся в SQLite с кешем 2 МиБ на индекс,
`mmap_size=0`, чтением по 128 строк и ограниченными транзакциями. Импорт одного
журнала атомарен: повреждённый gzip не подтверждает даже прочитанный префикс.
Конфигурации хранилищ и credentials в индекс не записываются.

Pending journal хранится на диске. Повторная загрузка ограничена числом записей
`flush_size` и примерно 16 МиБ исходного текста на gzip; отдельная запись ограничена
1 МиБ. Ошибка загрузки сохраняет pending records. Метаданные бэкапа публикуются через
последовательную JSON-запись с сохранением legacy-ссылок.

Это ограничивает память структур по числу объектов, но не обещает постоянный RSS
всего процесса: исходный `BackupMetadata` и его независимая целевая копия остаются
в памяти, как и текущий metadata-файл. Для scratch нужны свободный диск и приватный
`TMPDIR`; tar-spool и SQLite растут с объёмом данных. Нехватка диска должна завершать
copy ошибкой, а не публиковать неполный backup как `created`. Сравнивать нужно также
время, disk I/O, anonymous RAM и файловый кеш, а не только общий RSS контейнера.

Поле `unpacked` инвентаризации означает сумму содержимого metadata-файлов без
заголовков и padding tar. Оно не равно длине распакованного tar-потока.

Харнесс запускается на отдельной Linux VM с Docker. Для текущего сценария:
64 vCPU, 128 ГиБ RAM, SSD; рабочий каталог `/home/roaldm153/ch-backup`.
Исходный код `ch_backup/` не меняется: обёртки стадий и инструментирование
включаются только в процессах бенчмарка.

## Ускорение планирования и resume

Ветка `feat/copy-plan-speed` продолжает проверенный candidate `198e692`.
Его код `ch_backup` совпадает с `a64b0f6`, измеренным в серии
`20261102-ab-10000-retry`: 10k партов, 120 колонок, ClickHouse 26.3.12.3,
три обычных повтора. Медиана `plan_cloud_storage` выросла с 357 до 1005 секунд,
а `resume_filter` — с 14 до 193 секунд относительно исходного `127ea3c`.

В первых трёх CPU-окнах candidate 21–22% выборок главного потока попали в
`commit`, около 10% — в предварительный поиск ключа. Эти выборки включают ожидание
внутри вызова SQLite; они не доказывают, что всё это время потрачено на fsync.
Поздний `resume_filter` в окна не попал. Повторная запись оставшегося плана
подтверждена кодом; её вклад в замедление ещё нужно измерить отдельно.

Изменения для следующего A/B:

- Commit каждые 8192 записи вместо 512 при прежнем кеше 2 МиБ на индекс.
  Повреждённый импорт журнала по-прежнему откатывается целиком.
- Новый адрес сразу вставляется; поиск нужен только при дубликате.
  Проверка конфликтов источника и размера сохранена.
- Resume хранит диапазоны исключённых позиций и читает исходный план.
  Пути и размеры оставшихся объектов не записываются повторно; полный план
  файлов остаётся доступен для manifest. Кеш индекса диапазонов также ограничен.

Если исключено почти всё, чтение частичного плана всё ещё проходит по исходным
записям. Поэтому нужны полный smoke и проверки частичного resume; полностью
подтверждённый план повторно не читается. Работа с tar остаётся следующим шагом:
она заметна в профиле, но требует отдельной проверки формата и контрольных сумм.

После коммита изменений, на выделенной VM:

```sh
make test-benchmark-copy-memory-ab \
  BENCH_PARTS=10000 CLICKHOUSE_VERSIONS=26.3.12.3 \
  BASELINE_REF=198e692 CANDIDATE_REF=HEAD BENCH_REPEATS=3 \
  BENCH_ARGS='--total-budget-hours 24 --cleanup-timeout 1800'
```

Этот A/B отделяет ускорения от переноса структур на диск. Проверяем медианы времени
и CPU по этапам, пики RAM и disk I/O. Ускорение и неизменность пиков RAM пока
не измерены. Metadata-only resume не заменяет полный прогон с большим журналом.

## Запуск

После получения ветки подготовить версию пакета и инструменты:

```sh
cd /home/roaldm153/ch-backup
make ch_backup/version.txt
uv sync --group benchmark
tmux new -s copy-memory
```

Запуск профилирования требует root на хосте для чтения памяти процессов
контейнера через ptrace. На выделенной VM, из shell с правами root и доступным uv:

```sh
cd /home/roaldm153/ch-backup
set -o pipefail
make test-benchmark-copy-memory-overnight 2>&1 | tee overnight.log
```

Сначала проверить весь путь на небольшой точке (тоже с правами root):

```sh
make test-benchmark-copy-memory \
  BENCH_PARTS=50 BENCH_COLUMNS=10 CLICKHOUSE_VERSIONS=26.3.12.3 \
  BENCH_ARGS='--overnight --profile-repeats 1 --total-budget-hours 1'
```

`Ctrl+b`, затем `d` отсоединяет tmux; после этого SSH и ноутбук можно выключить.
VM должна продолжать работать. Не запускать две серии одновременно: окружение
интеграционных тестов использует общие staging-файлы.

## Ночной режим

По умолчанию это ClickHouse 26.3.12.3, 120 колонок, четыре worker-процесса
в каждом из пулов и точки 10/20/30 тысяч Wide-партов. Порядок: замеры 10k →
профили на тех же 10k → очистка → замеры 20k → профили 20k → очистка → 30k.
Профиль нельзя снять задним числом: после обычных замеров выполняются отдельные
повторы с py-spy и Memray на том же исходном backup. Маленькая контрольная точка
больше не добавляется; `--profile-parts` удалён.

`--repeats` задаёт число обычных повторов (по умолчанию 1; в цели A/B — 3),
`--profile-repeats` — повторов каждого профайлера (по умолчанию 1).
Порядок CPU/RAM меняется между профилируемыми повторами. Target-префиксы разделены
между повторами и инструментами; resume использует target соответствующего fresh.

На больших точках выполняются planning-only, а для metadata v5 ещё
metadata-only и его resume. Миллионы S3-объектов повторно не копируются.
Поэтому такой resume не моделирует большой журнал подтверждений и listing
скопированных объектов. Для них остаётся отдельный полный прогон.
Экстраполяции для full, planning-only и metadata-only разделены; профилированные
контроли и незавершённые прогоны в них не входят.

Профили и их отчёты готовы до перехода к следующему N. Увеличение N теперь увеличивает
стоимость профилирования. Один профилируемый copy ограничен `--profile-budget-hours`
(по умолчанию 2 часа) и оставшимся общим бюджетом. При его таймауте сохраняются
доступные артефакты, профиль отмечается неполным; уже собранные обычные замеры остаются.
Для больших N по умолчанию используется агрегированный Memray, описанный ниже.

Общий бюджет работы — 10 часов, включая подготовку окружения, INSERT, backup,
инвентаризацию и копирования. Начальная сборка wheel в Makefile проходит до
запуска таймера. Завершение процессов, сохранение логов, отчёт и очистка идут
после дедлайна. Очистка имеет отдельный предел `--cleanup-timeout` (1800 секунд).
Бюджет ограничивает длительность, но не гарантирует прохождение
всех точек: медленный FREEZE может израсходовать время раньше.

```sh
make test-benchmark-copy-memory-overnight \
  BENCH_ARGS='--total-budget-hours 12 --profile-repeats 1 --cleanup-timeout 1800'
```

При исчерпании бюджета серия получает `budget_exhausted`, не начатые точки —
`skipped_budget`, процесс возвращает 124. Ошибки возвращают 1; успешная серия — 0.
Итоговый статус хранится в `series.json`, статусы точек — в `point.json`.
Неполный профиль даёт точке статус `profile_incomplete`; серия продолжает остальные
точки, но завершится с ошибкой. Полезные замеры при этом сохраняются.
Обычная цель без `--overnight` сохраняет полный режим; лимит одной копии
настраивается через `--budget-hours` (по умолчанию 120 часов).

`point.json` содержит фазу `cleanup`, её состояние, начало/конец и `timings.cleanup`;
вывод команды сохраняется в `cleanup.log`. На таймауте завершается только клиент
очистки с его дочерними CLI-процессами. Docker может продолжать удаление на сервере.
Серия получает `cleanup_failed`, следующие точки — `skipped_cleanup`, код выхода 1.
Повторный запуск до проверки оставшихся контейнеров не нужен. Этот таймаут защищает
драйвер от бесконечного ожидания, но не устраняет замедление inode/writeback ядра.

## Что сохраняется

- `report.md`: инвентаризация активных партов без shadow-копий, пики и частичные
  результаты, отдельные прогнозы режимов, медианы и разброс контрольных прогонов,
  накладные расходы профайлеров, S3-гистограммы и ссылки на профили.
- `resources_*.png`: слой RSS по процессам, CPU и дисковый I/O. ClickHouse,
  SeaweedFS, ch-backup main/workers и инструменты наблюдения показаны отдельно.
  Группа clickhouse включает остальные процессы контейнера и подготовку backup.
- `telemetry/processes.jsonl`: внешние отсчёты RSS, CPU, I/O, переключений контекста,
  числа потоков. USS/PSS обновляются раз в пять секунд; недоступные значения — null.
- `telemetry/containers.jsonl`, `host.jsonl`: cgroup v2 memory/current/peak/stat/events,
  CPU throttling, I/O, PSI, свободная память/диск и swap. Отсутствующие показатели
  явно отмечены. Page cache контейнера не смешивается с Python heap.
- `samples.csv`, `stages.jsonl`, `progress.json`: текущая RAM и завершённые сегменты
  стадий. Сборщик работает отдельным процессом на хосте и не зависит от GIL ch-backup.
- `cpu-*.speedscope.json`: окна py-spy по 120 секунд при 49 Гц, максимум три окна
  на CPU-контроль, с `--subprocesses`. Открывать в [Speedscope](https://www.speedscope.app/).
  `cpu-windows.jsonl` содержит фактические границы окон; это выборки активных стеков,
  не полная трасса всех операций и не измерение ожидания S3.
- `memory-PID.bin`: отдельная запись Memray для основного процесса и каждого
  spawn-воркера. `observed.json` и `instrumentation-PID.json` проверяют покрытие.
  По умолчанию HTML `peak` показывает живые выделения на пике, `leaks` — оставшиеся
  к завершению записи; последнее само по себе не доказывает утечку.
  С `--memory-format all` дополнительно доступны `temporal` для выбора
  интервал, `temporary` — выделения, освобождённые в пределах 100 последующих
  выделений. Это не 100 миллисекунд. `stats.txt` содержит общий объём и число
  выделений. Heap, allocation traffic и RSS — разные метрики.
- `s3-PID.prom`: ограниченные Prometheus-гистограммы логических вызовов и реальных
  HTTP-попыток, ошибки и retries. Без меток с ключами, URL, заголовками и credentials.
  Задержка логического вызова включает retries, но не чтение streaming body
  GetObject после возврата. Перцентили в отчёте — верхние границы бакетов.
- `environment.json`, `system.txt`, `options.json`: версии Python/пакетов,
  Docker image ID, git revision, хеш исходников, настройки буферов/очередей,
  железо и параметры измерения. Конфиг с ключом шифрования в результаты не копируется.

`--trace-python-allocators` включает отслеживание отдельных Python-объектов;
по умолчанию оно выключено из-за большого объёма и накладных расходов.
`--native-profiles` добавляет нативные стеки
py-spy/Memray; для читаемых C-стеков могут понадобиться debug symbols.
Отдельный `--tracemalloc` включает прежний диагностический прогон; по умолчанию
он выключен. Тяжёлые профайлеры не запускаются одновременно.

Лимиты по умолчанию: 4 ГиБ сырых Memray-записей на точку и минимум 20 ГиБ
свободного диска. Превышение останавливает измеряемый процесс и отмечается как
ошибка, а не успешный результат. Интервал проверки — примерно секунда, это
не жёсткая файловая квота. HTML-отчёты требуют дополнительного места.

По умолчанию `--memory-format aggregated` использует штатный
`AGGREGATED_ALLOCATIONS`: файл содержит агрегаты по стекам на пике и при завершении.
Он существенно меньше полной трассы, но не поддерживает temporal/temporary/stats;
при SIGKILL до завершения Tracker пригодный RAM-профиль может отсутствовать.
Внешние `samples.csv`, стадии и телеметрия сохраняются независимо от Memray.
`--memory-format all` сохраняет каждое выделение без сжатия при выходе; этот режим
подходит для небольших точек и может дать частично читаемый файл при аварии.
Завершённые CPU-окна сохраняются
независимо от последующих. SIGKILL может повредить последнее окно/запись; пригодность
артефактов и отсутствующие воркеры отмечаются в отчёте. Последние несколько секунд
S3-счётчиков также могут не успеть записаться. Неуспешный профиль не используется
для оценки накладных расходов. HTML Memray использует локальные assets и скрывает
строки исходников; имена функций и файлов остаются.

Отчёт обновляется после backup и каждого copy, во время copy — раз в минуту.
После аварии его можно пересобрать на VM или локально без Docker:

```sh
uv run python -m tests.benchmark.copy_memory report staging/benchmark/RESULT_DIRECTORY
```

Если серия прервалась до генерации Memray HTML, на VM можно отдельно обработать
сохранившийся каталог одного прогона, затем пересобрать общий отчёт:

```sh
uv run --with memray==1.20.0 python -m tests.benchmark.copy_memory.profiles \
  staging/benchmark/RESULT_DIRECTORY/26.3.12.3/10000/profile_fresh_planning_memory_1-candidate \
  --timeout 900
```

Лимит построения каждого отчёта — 15 минут, отдельно от времени копирования.
`--timeout` меняет его в секундах при отдельной пересборке. Успешные непустые
отчёты переиспользуются, если они не старше сырого профиля; неуспешные,
отсутствующие и устаревшие строятся заново. Измеряемое копирование не повторяется.

Сырые профили сохранены для повторной обработки штатными командами
[Memray](https://bloomberg.github.io/memray/flamegraph.html) и
[py-spy](https://github.com/benfred/py-spy). `profiles.py` только вызывает их отчёты,
собственного формата профилировщика нет.
